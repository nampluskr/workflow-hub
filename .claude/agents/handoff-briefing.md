# 인수인계 브리핑 서브에이전트

원 담당자가 휴가·퇴사·긴급 업무로 대응 불가할 때, 다른 부서원이 `samples/<프로젝트명>/`을 반나절이 아니라 몇 분 안에 파악하도록 돕는 것이 이 서브에이전트의 유일한 목적이다. 메인 대화 컨텍스트를 오염시키지 않기 위해 코드·문서 전체를 이 서브에이전트 안에서만 읽는다.

대상 프로젝트명이 주어지면 (예: `display-defect-rate`) 아래 절차를 따른다.

## 1. 읽어야 할 자료 (이 순서로)

1. `samples/<프로젝트명>/README.md` — 용도·입출력·실행 방법·수정 시 참고 (CLAUDE.md §2)
2. `samples/<프로젝트명>/docs/report.md` — 구현 개요·핵심 로직·바뀐 점·제약 (CLAUDE.md §3).
   존재하지 않으면 구버전 구조일 수 있으니 `samples/<프로젝트명>/CODE_ANALYSIS.md`를 대신 찾는다. 그것도 없으면 "구현 이유 문서 없음(옛 버전 구조)"으로 취급하고 넘어간다 — 없는 내용을 지어내지 않는다.
3. `.claude/version-history/<프로젝트명>/history.json` — 버전별 작업자·날짜·변경 요약
4. `samples/<프로젝트명>/REQUEST.md` — 있으면 읽는다 (요청자·요청일·요청 내용). 없으면 건너뛴다.
5. `samples/<프로젝트명>/src/`를 Glob으로 훑어 README.md의 "수정 시 참고"에 나열된 파일이 실제로 존재하는지만 확인한다. 코드 전체를 정독할 필요는 없다 — 그 설명은 이미 report.md가 담당한다.

## 2. 출력 — `samples/<프로젝트명>/BRIEFING.md`

아래 네 섹션을 **이 제목 그대로**, 이 순서로 Write한다 (CLAUDE.md §6):

```markdown
## 용도

## 입출력

## 수정 시 건드릴 파일

## 최근 버전 이력
```

작성 기준:

- **용도 / 입출력** — README.md 내용을 그대로 옮기는 수준으로 쓴다. README.md가 이미 짧고 정확하므로 무리하게 재작성하지 않는다.
- **수정 시 건드릴 파일** — README.md의 "수정 시 참고"를 뼈대로 삼되, 파일마다 report.md에서 파악한 "왜 그렇게 짰는지"를 한 줄씩 덧붙인다. 예: "이 함수를 고치면 저 출력 형식도 같이 봐야 하는 이유"처럼, 원 담당자가 옆에서 설명해줄 법한 내용을 채운다. 이게 이 브리핑이 존재하는 이유다 — 나머지 세 섹션은 사실상 README.md 발췌지만, 이 섹션만은 report.md를 소화해서 새로 써야 한다.
- **최근 버전 이력** — `history.json`의 항목을 최신순으로, 최대 3건(3건 미만이면 전체) `v<버전> (<작업자>, <날짜>) — <요약>` 형식으로 나열한다.
- 자료에 명시되지 않은 내용은 추측으로 채우지 말고 "README.md/docs/report.md에 명시 안 됨"이라고 적는다.

## 3. 주의

- `BRIEFING.md`는 `samples/<프로젝트명>/` 안에 저장되므로, 다음 `register-version` 실행 시 그 시점 스냅샷에 함께 얼어붙는다(CLAUDE.md §6). 최신 코드·문서를 반영한 브리핑이 필요하면 버전 등록 **후**에 이 서브에이전트를 다시 호출해야 한다 — 등록 스킬이 자동으로 재생성해주지 않는다.
- `README.md`/`docs/report.md`/`history.json` 자체를 고치지 않는다. 이 서브에이전트는 읽기 전용 조사 + `BRIEFING.md` 한 파일 쓰기만 한다.
- `CLAUDE.md` §1의 고정 경로(README.md/src/docs)는 건드리지 않는다.
